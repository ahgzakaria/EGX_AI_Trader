## 4. Identity Conflicts

**18 conflicts discovered.** Discovered by rule, not by
consulting a hand-written list — see §4.3 for coverage of the named cases.

`Assessment` reports *observation*, never a corporate-action conclusion. A
ticker carrying feed traffic while its counterpart carries none is evidence;
calling that a rename is a judgement Phase 1 does not make.

**Read the `Canon Subscribed` column before trusting any row.** A canonical
ticker with no verified Rubix mapping contributes no subscription key, so the
collector never asks for it and it cannot possibly appear on the feed. For
those rows, "not observed" restates the universe's own configuration and is
**not** independent evidence. Only a subscribed-yet-silent counterpart
carries information in the negative direction — see §5.5.

### 5.5 What Rubix absence does and does not prove

This is the most important interpretive limit in the report.

The collector requests only symbols carrying a verified Rubix mapping. A
canonical row without one is never requested, so it can never be observed.
Treating its silence as proof that its ticker is retired would be circular:
the universe decided not to ask, and the answer is then quoted back as
evidence about the universe.

What each direction supports:

| Observation | Supports | Independent? |
|---|---|---|
| Workbook ticker observed on the feed | the exchange feed uses this identifier | YES |
| Canonical ticker silent AND subscribed | the identifier was requested and produced nothing | YES |
| Canonical ticker silent AND unsubscribed | nothing — it was never requested | NO |
| Workbook ticker never observed | either it is unsubscribed, or it is genuinely inactive | PARTIAL |
| Any ticker observed | the symbol is PUBLISHED on the feed — not that it traded | YES |

The last row is easy to misread. A `quotes` row can be an unchanged or
indicative snapshot, so observation proves publication, not execution — see
§6.1, where securities whose last EGX trade was in 2014 still carry a quote
from the current watermark.

A second confound: the database retains pre-migration history. **41** tickers were last
seen before the `2026-08-12` watermark, many on `2026-07-30` — the
canonical universe's own as-of date. Those are observations of a *previous*
subscription set. The `WB Observed Today` column in §4 separates current
traffic from historical traffic for exactly this reason.

Consequence for §7.2: `AIFI`, `AIHC`, `ELWA` and `MMAT` are archived and
therefore unsubscribed. Their last observations predate the watermark. Rubix
can neither confirm nor refute the workbook's claim that they traded on
2026-08-10, and no amount of further reading of this database will change
that. Resolving them requires a source outside these three.

### One precise caveat about the Rubix `-shm` file

Stated exactly rather than glossed: reading a WAL-mode SQLite database
requires mapping its `-shm` shared-memory index, so the `-shm` file's
modification time advances when this report runs. That is a consequence of
opening the database at all — the production collector's own readers do the
same — and it is **not** a change to database content: the `.db` and `-wal`
payloads are untouched, no page is written, no WAL frame is added, and no
checkpoint occurs. Verify by comparing `.db` and `-wal` digests before and
after a run; they are identical.

The alternative, `immutable=1`, would avoid touching `-shm` entirely but
instructs SQLite to ignore the WAL — against a live database with a very
large uncheckpointed WAL that would silently return stale data. Correct
evidence was preferred over an untouched timestamp.
