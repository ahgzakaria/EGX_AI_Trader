# Rubix Production Data Rollout Report

Date: 2026-07-14 (Africa/Cairo)

## Executive result

The production integration is implemented as a source and operational-safety change only. The frozen strategy signal is preserved verbatim. A separate post-decision layer now prevents stale Rubix data or Yahoo daily fallback from becoming a new actionable live BUY.

The production database is not present yet and no fresh user-supplied Rubix authentication frame was available to this validation run. Therefore the mandatory 30-minute live-market validation could not be performed and this report does **not** claim production readiness. In addition, the Phase 5 long-form reproduction detected changed Yahoo input candles/cache provenance; exact historical reference metrics do not reproduce with the currently refreshed Yahoo dataset.

## Production architecture

```text
Authenticated user session frame (supplied manually, never stored by EGX AI Trader)
        -> independent rubix_feed collector
        -> D:\EGX_AI_Trader\data\rubix_live_market.db (collector-owned)
        -> SQLite mode=ro RubixSQLiteProvider
        -> ProviderManager (timestamp comparison / explicit Yahoo fallback)
        -> unchanged indicators and frozen strategy
        -> post-strategy operational actionability
        -> Dashboard / Forward Testing / Paper Portfolio safeguards
```

EGX AI Trader does not log in, open a socket, read cookies, or write adapter tables. `RUBIX_DB_PATH` can override the production database path. Backtest routing remains Yahoo-only.

## Collector and launcher workflow

Double-click:

`scripts\start_rubix_production.bat`

The launcher requires a fresh auth-frame file exported manually from the user's current lawful Rubix session. It validates file existence, size, and age (maximum 15 minutes), but never reads or saves its contents. It then:

1. Loads the canonical active universe.
2. Starts the external `rubix_feed` package.
3. Subscribes in bounded batches.
4. Waits for SQLite schema, authentication acknowledgement, collector connection, at least one quote, and fresh provider status.
5. Starts Streamlit only after health succeeds, or asks for explicit permission to continue with Yahoo fallback.
6. Monitors child processes, quote age, coverage, and logs.
7. Terminates both children on Stop/close and force-kills only after a graceful timeout.

If the auth-frame field is empty, invalid, or older than 15 minutes, the launcher now shows the exact reason in its visible log and offers an explicit **Start Yahoo Only** path. That path is labelled `DAILY_FALLBACK / NON_LIVE` and never claims Rubix is active.

Equivalent collector invocation is generated by the launcher using the project virtual environment and the external package:

```text
python -m rubix_feed.cli --url wss://eg-feed3.mubashertrade.com/websocket/price --auth-frame-file <fresh-file> --database D:\EGX_AI_Trader\data\rubix_live_market.db --stale-seconds 60 --subscription-batch-size 100 --authenticated-session --symbol CASE~COMI ...
```

No command or log contains the authentication-frame contents. Common secret-bearing log fragments are redacted before display.

## Freshness policy

All timestamps are normalized against Africa/Cairo and regular EGX hours (Sunday-Thursday, 10:00-14:30).

| State | Evidence | Live BUY actionability |
|---|---|---|
| `FRESH` | receipt <= 60 seconds and 1-minute bar <= 2 completed minutes during open session | allowed when frozen strategy says BUY |
| `DELAYED` | collector receives data but exchange timestamp exceeds quote threshold | non-actionable |
| `STALE` | quote or generated bar exceeds its threshold, or completed-session lag exists | `DATA_STALE / NON_ACTIONABLE` |
| `SYMBOL_MISSING` | no Rubix quote/candle exists for requested symbol | fallback display only, non-actionable |
| `UNAVAILABLE` | DB missing, unreadable, or schema invalid | fallback display only, non-actionable |
| `YAHOO_FALLBACK` | Rubix unavailable/missing or not newer than Yahoo | `DAILY_FALLBACK / NON_LIVE` |
| `MARKET_CLOSED` | valid latest completed session outside regular hours | analysis allowed, no new live BUY |

The original `Signal` and `StrategySignal` remain unchanged. Only `OperationalStatus`, `FinalActionability`, `Actionable`, data source/timestamp/age, and the operational reason are added. A non-actionable BUY remains immutable evidence in the forward database, but it creates no alert, paper position, evaluation candidate, or Pending Signal.

## Known limitations

1. The dynamic authenticated session frame must still be supplied manually and must be fresh.
2. The canonical CSV currently has no exchange-maintained active/inactive field; no-update/rejected evidence must be reviewed after the 30-minute run.
3. Exchange holidays are not guessed by the weekday calendar. A healthy collector with no official session prints is surfaced for operational review.
4. Rubix database availability and coverage are currently zero because production collection has not started.
5. This integration is for scanning, forward testing, and paper operation. It does not authorize or implement real-money order execution.

## Verdict

**C. Not ready**

The engineering rollout and safeguards pass their automated tests, but the required production database, authenticated collector session, and 30-minute full-universe live validation are absent. Promotion to live Scanner/Forward Testing must wait for that observed validation. Automated real-money execution is not approved.
